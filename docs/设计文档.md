## 1. 产品定位与范围

**一句话**：给一桌 12 个朋友用的在线狼人杀，一个晚上连打数局，手机当法官。

### 明确要做的

- 12 人标准局，房主可自定义人数（6-18）和角色组合
- 手机自动播报流程（不需要真人当法官）
- 一晚上连打多局，战绩累积
- 完整警长竞选 + 白天手动推进（节奏由人控制）

### 明确不做的（这一版）

| 不做 | 原因 |
|---|---|
| 真人语音通话 | 需要实时音视频服务，成本与复杂度是另一个量级。用微信群语音代替 |
| 微信小程序 | 需要企业主体 + 备案域名。H5 已经够用，且后端可复用 |
| 公开推广 / 引流 | 《微信外部链接内容管理规范》2.5 把 H5 游戏列为违规。只私聊发给 12 个朋友 |
| 跨服务器分布式 | 单进程内存 + 单 JSON 文件足够。房间规模决定了不需要 |

### 部署前提

- 一台常驻的机器（本地电脑 / 轻量服务器）
- HTTPS（PWA 安装和微信内体验都需要）
- 合规与部署细节见 `微信接入指南.md`、`部署指南.md`

## 2. 层级模型（最重要的一节）

```
账户（人）
 └─ 大厅 ─────────────── 「今晚这一桌」
     ├─ 名册           谁在场
     ├─ 战绩           大厅内有几局、谁赢了几局
     └─ 局 ───────────── 「桌上的第几局」
         ├─ 座位 / 人数 / 版型
         ├─ 局房主       这一局谁在控场
         └─ 轮次
             ├─ 夜晚：狼人 → 守卫 → 女巫 → 预言家（定时）
             └─ 白天：警长竞选 → 发言 → 放逐投票（全手动）
```

### 三层的职责

| 层 | 生命周期 | 保存什么 | 谁有权限 |
|---|---|---|---|
| **账户** | 永久 | 昵称、密码哈希、累计战绩 | 本人 |
| **大厅** | 一晚（保留最近 20 个） | 名册、局列表、大厅内战绩 | 厅主 |
| **局** | 建到删 | 座位、版型、对局全过程 | 厅主 + 局房主 |
| **轮次** | 分钟级 | 当前阶段、行动、投票 | 引擎自动 |

### 关键约束

- **同一时刻，一个大厅只能有一个「进行中」的局。** 想同时开两桌 → 建两个大厅。
- **进大厅 ≠ 进局。** 大厅可以有很多人，但一局只坐得下「版型人数」那么多人。多出来的人在厅里等，或旁观。

## 3. 账户系统

### 注册与登录

- 昵称 + 密码
- **昵称全局唯一**，不能重复（会做即时校验）
- 密码用 Node 内置 **scrypt** 哈希存储，绝不明文
- 登录后浏览器本地保存凭据，**下次打开自动登录**

### 为什么需要账户

1. 认出「我」→ 找到我建过的大厅、我的战绩
2. 解决「清了浏览器缓存就认不出人」的问题

### 边界

| 情况 | 处理 |
|---|---|
| 忘记密码 | 不做找回。换个昵称重新注册（这个场景下够用） |
| 清了缓存 | 重新输昵称+密码登录，战绩还在 |
| 局进行中换设备登录 | **不允许顶替座位**（会踢掉正在玩的人），可以旁观 |

## 4. 大厅

### 创建与加入

- 输网站 → 两个按钮：**创建大厅** / **加入大厅**
- 创建者 = **厅主**
- 其他人用**大厅号或分享链接**加入
- 加入后大厅显示各自的昵称

### 厅主的主页面

厅主登录后能直接看到：
- 自己建的大厅列表（最近 20 个）
- 每个大厅里打了几局、每局结果

### 玩家在大厅能看到什么

**自己**：当狼几次、当神几次、当民几次、赢几局输几局
**别人**：胜负信息

### ⚠️ 战绩的铁律：局结束后才刷新

**这一条如果做错，整个游戏就毁了。**

如果「当狼次数」在发牌那一刻就更新，那么：

> 第 3 局开始前老王显示「当狼 1 次」。发牌后刷新变「当狼 2 次」——
> **所有人立刻知道老王这局是狼。**

**所以：**

- 统计只在**一局分出胜负后**才写入和显示
- 游戏进行中，大厅里**不显示任何本局数据**，更不显示实时变化
- 这条会用测试锁死

## 5. 局

### 局的参数

| 参数 | 说明 |
|---|---|
| 人数 | 6-18，房主定 |
| 版型 | 角色组合，总数必须等于人数 |
| 座位 | 按人数生成，玩家自行进入占座 |
| 局房主 | 控场者（默认厅主，可授权给别人） |

### 生命周期

```
未开始 ──房主点「开始游戏」──▶ 进行中 ──分出胜负──▶ 已结束
   ▲                              │                    │
   └────── 重开（丢弃进度）────────┘                    │
                                                       ▼
                                              自动保存为一条记录
```

### 各状态的行为

| 状态 | 谁能做什么 |
|---|---|
| **未开始** | 玩家进入占座、点就绪；房主改人数/版型、点开始 |
| **进行中** | 只能操作自己（上警/投票/行动）；房主推进流程、可结束或重开 |
| **已结束** | 所有人可浏览细节；**厅主**可修改或删除这条记录 |

### 已结束的局能看什么

- 全场身份（谁是什么牌）
- 每一轮发生了什么
- 票型（谁投了谁）
- 死亡复盘（谁在第几天、因何出局）

## 6. 权限模型

### 四种角色

| 角色 | 怎么产生 |
|---|---|
| **厅主** | 建大厅的人 |
| **局房主** | 厅主本人，或被厅主授权/同意的玩家 |
| **普通玩家** | 大厅成员 |
| **游客** | 大厅成员，但没进这一局（人数满了） |

### 权限表

| 操作 | 厅主 | 局房主 | 普通玩家 | 游客 |
|---|---|---|---|---|
| 改人数 / 版型 | ✅ | ✅（本局进行中） | ❌ | ❌ |
| 开始 / 结束 / 重开本局 | ✅ | ✅ | ❌ | ❌ |
| 推进白天流程（警长/公示） | ✅ | ✅ | ❌ | ❌ |
| 授权房主 | ✅ | ❌ | ❌ | ❌ |
| 改 / 删已结束的局 | ✅ | ❌ | ❌ | ❌ |
| 查看已结束的局 | ✅ | ✅ | ✅ | ✅ |
| 看上帝视角 | 局内且存活则 ❌ | 同左 | 同左 | ❌ **一律不给** |

### 「局房主」的授权流程

1. 厅主先创建第 N 局
2. 其他玩家点「申请当房主」
3. 厅主同意 → 该玩家获得这一局的控制权
4. **厅主始终保留同样的控制权**（不是互斥的）

### 临时操作权（掉线兜底）

- 房主消失 **超过 60 秒** → 界面提示「房主不在」
- **任何在线玩家**可点「我来接管」拿到临时控制权
- 房主回来 → **自动收回**；若临时房主有未完成动作，等它做完
- 房主一直不回来 → **临时权限一直有效，含结束/重开本局**（否则会变成没人能收场的死局）

> 之所以不「一断线就移交」：房主切个微信回条消息（20 秒）就被夺权，他切回来会发现「我不是房主了」，很懵。

## 7. 版型配置

### 交互

**先定人数，再配角色。**

- **可数角色**（用 +/- 调数量）：狼人、平民
- **唯一角色**（0 或 1）：预言家、女巫、猎人、白痴、守卫、摄梦人、白狼王、狼王、通灵师、机械狼、混血儿、舞者、假面

### 校验规则（由服务端判定）

| 规则 | 违反时 |
|---|---|
| 角色总数**必须等于**人数 | 拦住开局，并提示「还差 3 个」或「多了 2 个」 |
| 唯一角色最多 1 个 | 拦住 |
| 至少 1 名狼人 | 拦住 |
| 至少 1 名好人 | 拦住 |
| 狼人占比 > 45% 或 < 20% | 只警告，不拦 |

### 夜晚顺序由版型决定

**板型里有哪个夜间角色，就播报哪个。** 没有守卫的板型不播守卫阶段——这不泄露信息，因为**板型本身是公开的**。

## 8. 夜晚流程

### 顺序

```
天黑请闭眼
  → 狼人请睁眼，请确认战术     （固定 90 秒）
  → 狼人请闭眼
  → 守卫请睁眼                （固定 20 秒）
  → 守卫请闭眼
  → 女巫请睁眼                （固定 25 秒）
  → 女巫请闭眼
  → 预言家请睁眼              （固定 20 秒）
  → 预言家请闭眼
天亮了
```

### ⚠️ 铁律：夜间的时间不能携带任何信息

这一条是玩家发现的，必须严格遵守：

**每个夜间角色阶段，每晚都固定走完，不管这个角色是死是活、有没有事做。**

反例（错误做法）：

```
女巫还有药  →  狼人 → 女巫 → 预言家
女巫没药了  →  狼人 →        预言家     ← 阶段消失，等于告诉全场「女巫没药了」
```

后面的夜晚狼队就会毫无顾忌地刀女巫，因为不用怕解药了。**而"女巫还有没有药"是天亮不会公布的隐藏信息。**

**同样地：不能因为「某个角色的玩家暂时离开」而暂停计时。** 一暂停就等于宣布"这个阶段有人在操作"，也就是"这个角色还活着"。

### 因此的规则

| 条件 | 能不能暂停 |
|---|---|
| **所有人都掉线** | ✅ 可以（没人看着，不泄露任何东西） |
| **个别角色离开** | ❌ 绝对不行 |
| 某角色已死 | ❌ 阶段照常走完 |
| 某角色无事可做（如女巫没药） | ❌ 阶段照常走完 |

### 倒数提醒

- 每个阶段的**最后 5 秒**，界面显示大号数字，语音念 5、4、3、2、1
- **倒数是提醒，不是终止信号**
- 因为阶段总时长固定，倒数本身不携带信息

### 「结束本轮」

- 任何人都可以按，提前结束当前夜间回合
- 不影响信息（"某角色活到第几夜"在天亮就公布了，提前结束推不出新东西）

### 各角色的夜间规则

| 角色 | 规则 |
|---|---|
| **狼人** | 各狼独立点刀，多数票生效；平票或多数选「空刀」则平安夜 |
| **白狼王** | 属于狼营，和狼一起睁眼点刀（没有单独的阶段） |
| **守卫** | 守护一人免疫狼刀；**不能连续两晚守同一人**；**同守同救时该人依然死亡**；挡不住毒药 |
| **摄梦人** | 每夜必须选择另一名存活玩家；梦游者免疫当夜夜间伤害；连续两夜梦同一人则目标出局；摄梦人夜死会带走梦游者 |
| **女巫** | 解药/毒药各 1 瓶，全局一次；**同一夜不能双药**；默认不可自救 |
| **预言家** | 查验一人阵营 |
| 猎人 / 白痴 / 平民 | 夜里无行动 |

### 夜晚结束的结算

1. 判定狼刀是否落在目标身上（守卫 / 解药 / 同守同救）
2. 毒药生效（无视守护）
3. 消耗药水
4. 记录守卫这一夜守了谁
5. 摄梦结算：梦游者先免疫基础夜间伤害，再判定连续摄梦或摄梦人夜死连带
6. 触发死亡开枪（摄梦死亡会压制猎人和狼王技能）

## 9. 白天流程

### 为什么白天不用计时器

白天要真人发言、要讨论。竞选发言和白天发言阶段给足长时间，房主可以在全员说完后手动推进；超时仍会自动推进，避免房主掉线把整局永久卡死。

### 第一天：警长竞选

| 步骤 | 说明 |
|---|---|
| 1 | 每个人出现 **「我要上警」/「不上警」** 二选一（必须表态，否则房主不知道谁还没决定） |
| 2 | 上警名单在座位盘实时可见，进度条显示还有多少人未表态 |
| 3 | 全员表态后生成**警上发言顺序**；超时未表态按不上警处理 |
| 4 | 顺序**随机决定方向**和起点 |
| 5 | 警上依次发言（**不计时**） |
| 6 | 警上的人可以按**「退水」**，退水后全场立刻可见 |
| 7 | 警下的人给**还在警上的人**投票（**退水者不能被投**） |
| 8 | 大家投完后自动锁票并公布谁给谁投；超时未投按弃票处理 |

**当选**

- 得票最多者当选警长
- 该玩家手机上语音播报 **「金色传说」**
- 其他开着语音播报的玩家也播一遍（让全场都知道）

**平票**

- 首轮平票的候选人进入 PK 发言，非候选人重新投票
- 重新投票仍平票 → **警徽被撕掉**，本局不再有警长

> ⚠️ 只有第一天选警长。

### 白天发言

- 按警长决定的顺序（无警长则按座位顺序）依次发言
- 警长在页面选择顺时针或逆时针；警长最后发言并归票
- 房主看着大家发完后推进；超时也会自动进入投票，防止房间永久卡住

### 放逐投票

| 规则 | 说明 |
|---|---|
| 随时可改 | 每个玩家在「房主公示之前」可以任意改自己的票 |
| 房主公示 | 房主点「公示」才锁定，并显示谁投了谁 |
| **防手滑** | 点公示**必须先弹窗确认** |
| **平票** | 平票的玩家**再 PK 一轮**（重新发言 + 重投） |
| **再次平票** | **白天无人出局**（平安日） |

### 放逐结算

- 被放逐者出局
- 若是**白痴** → 翻牌免死，永久失去投票权，不再是投票目标
- 若是**猎人** → 可以开枪（被狼刀死或放逐可开枪；**被毒死、被白狼王带走不能开枪**）
- 若是**警长** → 移交或撕毁警徽（见下）

### 警徽移交

- **死亡的警长，在白天第一时间选择另一名存活玩家接任**
- 新警长当选 → 同样播报「金色传说」
- 若无人接任 / 选择撕毁 → 语音播报「本局没有警徽」
- 警长的放逐票按 **1.5 票**计算，票型会标明权重

### 狼人自爆（白天可用）

- **白狼王**：自爆并**带走一名玩家**（也可不带），爆后进入指定目标阶段
- **普通狼人**：**空爆**——不带人，爆完直接结算进黑夜
- 两者共同规则：
  - 允许时机：警长竞选的 5 个子阶段 + 白天发言 + 放逐投票（夜晚不可）
  - 自爆后**立刻进入黑夜**，当天不再发言与投票
  - 自爆发生在**警长竞选期间** → 竞选终止、**本局警徽流失**（第二天不会重选）
  - 警长已产生后自爆 → 不撕警徽，走正常的移交/撕毁流程，移完才进黑夜
- 白狼王的胜负判定在**带人之后**进行；普通狼空爆后立即判定
- 狼王（黑狼王）、机械狼、假面等特殊狼**没有**自爆按钮

## 10. 语音播报

### 开关规则

| | 默认 | 什么时候能改 |
|---|---|---|
| 房主 | **开** | 大厅 + 白天 |
| 其他玩家 | **关** | 同上 |

**天黑期间任何人都不能改**（防止有人夜里临时开语音搞场外因素）。12 台手机同时念会互相干扰，所以默认只有房主开。

### 技术限制

用的是**浏览器内置的语音合成（TTS）**：

- ✅ 不需要麦克风权限、不需要录音
- ❌ **没有音色库**——「金色传说」只能念成机器音，无法真的模仿炉石口吻

想要真音效需要**提供音频文件**（注意版权）。这一项见第 14 节。

### 台词铁律

**台词只能包含公开信息。**

反例（错误做法）：女巫阶段念「今晚 5 号被狼人杀害」——那等于用喇叭把狼人的选择广播给所有人。

正确：女巫阶段只念「女巫请睁眼」。

**这条会有测试兜底：同一阶段所有人的台词必须完全一致。** 一旦有人拿到不一样的台词，就说明掺进了隐藏信息。

## 11. 信息隔离原则 ★

这是整个产品的核心，所有功能都要过这一关。

### 原则一：服务端权威

- 所有规则判定在服务端
- 客户端只拿到**为自己过滤后的视图**（预言家只有自己的验人结果，狼人只看到狼队友）
- 客户端不做任何规则判断

### 原则二：时间不能作为信息通道

- 夜间阶段**时长固定**，不因角色状态变化
- **不跳过任何阶段**（板型里有的都要走）
- **不因个别玩家离开而暂停**
- 只有「所有人都掉线」才能冻结

### 原则三：隐藏信息不能在游戏进行中泄露

| 信息 | 什么时候能公开 |
|---|---|
| 别人的身份 | 游戏结束后 |
| 死因（被刀还是被毒） | 游戏结束后（天亮只公布"谁死了"，不公布原因） |
| 女巫还有没有药 | 游戏结束后 |
| 胜负结果 | 进入结算阶段时 |
| **战绩统计** | **一局结束后**（否则发牌瞬间就泄露身份） |
| **「这个人能自爆」** | **只在身份牌点开时可见**：自爆/空爆按钮渲染在身份牌卡内，卡合上时界面无任何痕迹；公共阶段提示词对所有角色一字不差。曾经给狼人的公开提示写过「你也可以自爆」，同屏瞄一眼就等于验明狼身——已删 |

### 原则四：上帝视角是自愿行为

| 我是谁 | 能不能看 |
|---|---|
| **在局内、还活着** | ❌ **看不到**（连按钮都不出现） |
| **在局内、已出局** | ✅ 能看到 |
| **游客**（大厅成员但没进这一局） | ❌ **看不到**（见下） |
| 游戏已进入结算（GAME_OVER） | ✅ 所有人可见，不用申请 |

- 点之前**必须弹窗确认**：说明会看到全场身份、等于放弃公平性

> **这是服务端权威，不是界面隐藏。** 权限判断在 `Game.mayUseGodView()` 里，
> 活着的玩家伪造一个 `game.godView` 请求，engine 会直接拒绝、并且不下发 `revealAll`。
> 只在客户端藏按钮是纸糊的权限 —— 改一行 JS 就能把全场身份拉到手上。

> 这是**信任机制**，不是技术保障 —— 能看到的人可以用微信给别人报信。熟人局够用。

#### 为什么游客也看不到（已定，不再加开关）

原本的设计是「游客能看」。实现时发现一个绕不过去的问题：

**服务端无法区分「真游客」和「拿着旧 token 的活人」。** 一个人用小号或者另一台手机
进大厅当"游客"，就能合法地把全场身份看在眼里，再念给场上的人听 —— 而这在界面上
和真游客完全一样，没有任何特征可以拦。

所以最终决定：**一律拒绝**，也不加开关（熟人局用不上，加了反而多一个能开挂的口子）。

## 12. 掉线与容错

### 「在线」的三层信号

| 信号 | 速度 | 含义 | 用途 |
|---|---|---|---|
| **页面切后台**（客户端主动上报） | **立刻、可靠** | 他可能在回微信 | 界面提示 |
| **连接断开** | 延迟几十秒到几分钟 | 连接真没了 | 判断"所有人掉线" |
| **长期无活动** | 分钟级 | 人真走了 | 清理会话 |

**注意**：手机息屏 / 切应用**不一定立刻掉线**。WebSocket 的协议层心跳由浏览器原生实现，不需要 JS 参与，所以连接可能保持很久。不同手机表现不同，**以真机实测为准**。

### 冻结规则

> **没有人在场时，局不推进。**

| 场景 | 行为 |
|---|---|
| 所有人都不在线（夜里） | **整局冻结**，计时器暂停 |
| 有人回来 | **解冻**，当前阶段**重新计时**（不补算流逝的时间） |
| 白天 | 本来就是手动等人，自然不推进 |

这一条同时解决了：服务器重启恢复、夜里全掉线导致空刀推到底、玩到一半关电脑、房主掉线卡死。

### 重连恢复

- 同一浏览器重新打开 → 自动用本地凭据登录、**自动回到原座位和身份**
- 微信切后台再切回来 → 客户端**立刻主动重连**（不等系统回收连接）
- iOS 内存回收导致页面重载 → 同上，自动恢复
- **服务端重启** → 房间已从数据库恢复，老 token 重连同样回到原座位继续打（见第 13 节）

### 已知的技术缺陷（要修）

当前服务器心跳只发 ping、**不检查 pong**，所以检测不出死连接。要改成标准做法（收到 pong 才算活）。

## 13. 数据持久化

### 落盘的内容

```
账户            昵称、密码哈希、累计战绩
大厅            名册、局列表、每局战绩
已结束的局      完整记录（身份、票型、复盘、死亡记录）
进行中的局      引擎状态（阶段、行动、投票、私有信息）
```

### 不落盘的

- **在线状态**——存不了，也不可能存。重启后所有人都是离线，等他们陆续回来
- **计时器剩余秒数**——停机期间已到点的阶段按超时结算，之后的阶段重新计满时长

### 进行中对局的持久化（已实现）

房间每次状态变化（入座/就绪/行动/阶段推进/连接变化）都会把**整间房**序列化成
纯 JSON 写进 `room_snapshots` 表（`setImmediate` 合并连发变更，不拖慢消息处理）。
写入内容：座位与 token→用户映射、版型/模式、海克斯选牌、对局引擎全套状态
（含私有信息与随机流断点）。服务端启动时逐条恢复；恢复失败（格式过旧/损坏）
的快照直接丢弃并删除，不影响其余房间。

恢复语义：

- **玩家侧**：老 token 重连即落回原座位，看到的个性化视图与重启前一字不差
  （快照虽是上帝视角，但只落库、绝不下发，视图仍由引擎按人裁剪，有测试钉住）
- **时间侧**：停机期间流逝的时间有效——已到点的阶段按超时结算
  （与服务端在线时挂机的自动处理是同一条代码路径），之后的阶段重新计满
- **优雅退出**：SIGINT/SIGTERM 先同步补一次落盘；进程被强杀时最多丢最后一步操作

### 保留策略

- **账户**：永久
- **大厅**：**保留最近 20 个**，更早的自动清理
- 局跟随大厅一起清理

### 技术选型（当前实现）

账号、大厅归属、已结束场次与统计使用 SQLite 兼容数据库：本地默认文件为
`data/werewolf.db`；部署时可通过 `TURSO_DATABASE_URL` 和 `TURSO_AUTH_TOKEN` 连接 Turso，
避免无持久化磁盘的平台在重启后丢失数据。密码只保存带随机盐的 `scrypt` 哈希。
进行中的房间按上一节的机制快照进同一数据库，服务端重启后自动恢复。

删除场次采用软删除：场次从所有玩家列表和累计统计中消失，但数据库中保留删除时间与操作者，便于后续审计或恢复。

## 附：设计原则备忘

写下来免得以后忘：

1. **服务端权威**——客户端只拿过滤后的视图，不做规则判断
2. **时间不是信息通道**——夜间时长固定、不跳阶段、不为个别人暂停
3. **隐藏信息在结束后才公开**——身份、死因、药水、战绩
4. **台词只念公开信息**——同一阶段所有人的台词必须一致
5. **宁可拒绝，不可猜测**——不确定的操作就报错拒绝，不要静默替玩家做决定
6. **防手滑**——不可逆的操作（公示、解散、结束本局）都要二次确认
